# Plan: C1, a real cluster

Status: proposed 2026-11-15, waiting for the owner's OK. C1 is not in the unattended queue. Edit the choices
below, or say OK; the steps then run one PR each, and this file is deleted when the last one merges.

## Goal
market-rates runs on a cluster, deployed by merging a promotion PR, and GitHub shows whether the rollout worked.
That is the last build step before the week of unattended maintenance (ADR 0029). Minimal: nothing from the
"Waiting for a real cluster" list is built unless it is named here.

Already decided (ADR 0029 amendment): Oracle Cloud Always Free, one ARM VM in an EU region, single-node k3s, Flux
in the cluster pulling from git, no cluster credentials in GitHub.

## What I checked
- market-rates and its image `ghcr.io/nabiabdallah/market-rates` are public (anonymous clone and pull both
  answer 200), and so is claude-factory. Flux and the kubelet need no GitHub credentials.
- market-rates has no database, no login and no secrets. It keeps rates in memory and each replica polls Binance
  by itself (8 calls per 10 s per replica). Nothing has to be created in the cluster for it but namespaces.
- CI builds the image for amd64 only (Jib's default). An ARM node can't run it.
- Deploy files are `risk:high` in services, so every promotion PR waits for you. That stays.
- k3s enforces NetworkPolicy itself, so the template's default-deny policy is live from the first deploy. Egress
  443 is open, which is all Binance needs. The OTLP collector address stays a placeholder (spans are dropped).

## What gets built

### Step 1: java-pipeline 0.22.0 (claude-factory PR; both templates)
- **`ci.yml`, image job:** build for `linux/amd64` and `linux/arm64` (`-Djib.from.platforms`; the pinned
  distroless digest is a multi-arch index). cosign signs the index and both images (`--recursive`); the SBOM
  attestation goes on the index. No factory-parent release: the flag is in the workflow.
- **`ci.yml`, verify job:** the Trivy scan runs on both architectures' tarballs (Jib builds a tarball for one
  platform at a time).
- **`promote.yml`** (decision 6) and its script: picks the commit, checks its image exists for both
  architectures, changes `newTag` in one overlay, opens the PR as the App. `check-deploy.sh` judges it as today.
- **`post-deploy.yml`:** runs on the `status` event. A failed `flux/*` status opens (or updates) an issue
  `Deploy failed: <env> at <sha>` in the service repo with Flux's message; a later success closes it. This is the
  first piece of the alert-to-issue loop, and what the weekly digest can count later.
- README "Deploy" section, CHANGELOG with an **Upgrading** note, `ci/test-promote.sh` (commit choice, missing
  image, unchanged tag) and `ci/test-post-deploy.sh` (failure opens once, success closes, other contexts ignored).

### Step 2: `cluster/` (claude-factory PR)
- **`cluster/cloud-init.yaml`:** Ubuntu 24.04 arm64; opens the host firewall the way k3s needs on Oracle's image;
  installs k3s and the Flux controllers, both pinned by version and sha256; creates one Flux source on
  claude-factory `main`, path `cluster/services`. The Kubernetes API is not opened to the internet.
- **`cluster/services/market-rates.yaml`:** the two namespaces, a service account per namespace that may only
  change its own namespace, a Flux source on market-rates `main`, and one Flux Kustomization per overlay
  (`wait: true`, 5 min timeout, `prune: true`, running as that service account, so a merged PR in a service repo
  can't touch anything outside its namespaces). An Alert and a GitHub Provider post the status (decision 4).
- **Factory CI:** `cluster/` renders and matches the schemas (kubeconform with the Flux CRD schemas, pinned);
  `cluster/**` is `risk:high` in the factory's classifier.
- **`docs/CLUSTER.md`:** the runbook: create the VM, create the status token and its secret, look at the cluster
  over SSH, register a service, roll back (a revert PR; `check-deploy.sh` already refuses one that crosses a
  migration), rebuild the VM from nothing.
- **ADR 0034** (pull-based CD, statuses as the post-deploy check, what is deferred). Roadmap.

### Step 3: you
Create the VM from the runbook (Always Free ARM shape, 4 cores, 24 GB, SSH key, paste the cloud-init), create the
status token, and run the one `kubectl create secret` line from the runbook on the VM.

### Step 4: acceptance on market-rates
1. A session opens the 0.22.0 upgrade PR on market-rates (workflow files only; you merge it, it is `risk:high`).
2. `promote.yml` for staging, you merge: the commit gets a green `flux/market-rates-staging`. Then prod.
3. One failure on purpose, in staging: promote a docs-only commit (on main, but CI built no image for it, so
   `check-deploy.sh` passes and the pull fails). Expected: the old pods keep serving, a red status after 5 min,
   an issue opened; the revert PR turns it green and closes the issue.
4. Roadmap: C1 ✅, the maintenance week starts, "Waiting for a real cluster" loses "A CD job".

## Risks and limits
- **ARM capacity.** Oracle often has no free ARM capacity in busy regions; creating the VM can take retries.
- **One node.** A VM reboot is an outage; the PodDisruptionBudget and three replicas change nothing about that.
- **Flux polls** (1 min): no inbound webhook, so a merged promotion starts rolling out up to a minute later.
- **The status token expires** (a year at most). Until the digest tracks it, an expired token means rollouts
  still happen but report nothing. The runbook says how to replace it.
- **Three things I will confirm while building, not from memory:** that Jib's tarball build takes one platform
  per run, that the pinned Flux release's GitHub provider posts a status per Kustomization, and the firewall
  rules Oracle's Ubuntu image needs for k3s. If Flux can authenticate as the factory App instead of a personal
  token, I will propose that in step 2's PR.
- **I can't test the cluster from a session.** Factory CI checks that the files render and the scripts behave;
  the first real proof is step 4.
